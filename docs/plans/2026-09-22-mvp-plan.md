# Bioregional Passport — MVP Implementation Plan (session plan)

**Spec (binding authority):** `docs/build-set/10-passport-prd.md` (B1), `11-passport-technical-architecture.md` (B2), `12-passport-protocol-schema-reference.md` (B3), `13-passport-implementation-plan.md` (B4). Where this plan deviates from the build set for MVP scope, the deviation is listed in §2 and recorded as an ADR in `docs/adrs/`.

**Goal of this plan:** a deployed, working MVP at https://bioregionalpassport.org that proves the product vision end to end in a browser: pod provisioning from a manifest (Boulder + tenant zero), a web wallet with the in-person attestation ceremony, membership + tier VACs from a policy enforcement point, a trust index with explanations, a verifier SDK, open records on a map/directory, a grants round with quadratic voting, and a mutual-credit circulation module with a two-leg payment. Phase order follows B4 §5 for a small team: 0 → 1 → 3 → 2 → 5 → 4.

## 1. Global constraints (binding for every task)

- **Language/tooling:** TypeScript strict, ESM (`"type": "module"`), Node 22, pnpm workspace + Turborepo, vitest 5 for tests. Every package: `src/index.ts` entry, `tsconfig.json` extending `../../tsconfig.base.json`, scripts `build` (tsc -p tsconfig.json → dist), `typecheck` (tsc --noEmit), `test` (vitest run). Package names are `@passport/<name>`. Packages export from `dist` (`"exports": {".": {"types": "./dist/index.d.ts", "import": "./dist/index.js"}}`) except `apps/*`.
- **No web3 vocabulary anywhere in UI copy** (no "token", "chain", "wallet address"). "Passport", "credential", "credits", "neighbor", "vouch".
- **Crypto:** `@noble/curves` (ed25519), `@noble/hashes` (sha256, hkdf), `@scure/base` (base58btc, base64url), `canonicalize` (RFC 8785 JCS). No `node:crypto` in packages that must run in the browser (credential-core, verifier-sdk, pod-client, wallet).
- **VC profile (B3 §2):** VC 2.0; `@context` = `["https://www.w3.org/ns/credentials/v2","https://firstperson.network/credentials/dtg/v1","https://bioregion.org/credentials/v1"]`; `proof.type = "DataIntegrityProof"`, `cryptosuite = "eddsa-jcs-2022"` implemented per W3C: `hash = sha256(jcs(proofConfig)) || sha256(jcs(document-without-proof))`, signature ed25519, `proofValue = "z" + base58btc(sig)`. Digest: `"z" + base58btc(multihash(0x12, sha256(jcs(credential-with-proof))))`.
- **Identifier profile for MVP (ADR-21):** personas and pairwise identifiers are `did:key` (Ed25519, multicodec 0xed01) carrying `credentialSubject.bioregionScope ∈ {"public","directed","pairwise"}`. Pods, groups and platform are `did:web` hosted at `https://<PLATFORM_DOMAIN>/dids/<slug>/did.json` (resolver also accepts a static map for tests). `did:webvh`, `did:peer`, `did:plc` are follow-ups; resolver interface `resolve(did) → DidDocument` must stay method-agnostic.
- **Authority scopes:** exactly the strings in B3 §3. Tier defaults per B3 §3.
- **Tenancy (B2 §2.3):** every pod-service call resolves a tenant slug in this order: custom domain → `<slug>.<PLATFORM_DOMAIN>` → `/p/<slug>` path prefix → `X-Pod` header. Services refuse a presentation whose pod DID ≠ resolved tenant's DID with error code `POD_MISMATCH`. **No cross-pod query path**: every pod query runs inside `withPod(slug, ...)` which sets `search_path` to `pod_<slug>`. Platform tables live in schema `platform`.
- **Errors:** JSON `{ code: string, message: string, hint?: string }` with proper HTTP status. Every gate explains itself in one plain sentence in `message`.
- **Service handlers are framework-agnostic:** `services/*` export `createXHandlers(deps)` returning functions of the shape `(ctx: PodContext, input) => Promise<Output>` plus a `routes` table `{ method, path, handler }`. `apps/web` mounts them. `PodContext = { slug, podDid, db: PodDb, manifest: BioregionManifest, policy: TrustPolicy, now: () => Date }`.
- **Tests:** unit tests colocated `src/**/*.test.ts`. DB tests use PGlite (`@electric-sql/pglite`) via `createTestDb()` from `@passport/db`; never hit Neon in tests. Every task's tests must pass with `pnpm --filter <pkg> test` and typecheck must pass.
- **Commits:** conventional commits `feat(scope): …`; commit only your own package paths; if `.git/index.lock` exists, wait 2s and retry (other agents share the worktree).
- **Licence headers:** none required. Apache-2.0 at root.

## 2. MVP deviations from the build set (each becomes an ADR file in `docs/adrs/`)

- ADR-21 `did:key`/`did:web` for MVP instead of `did:peer:4`/`did:webvh`/`did:plc`.
- ADR-22 Ceremony transport is QR + an HTTP relay (`services/pod-vta` relay endpoints) with an IndexedDB outbox in the wallet instead of DIDComm/mediator. Message names and bodies follow B3 §5 exactly so DIDComm can carry them later.
- ADR-23 Ledger is a native mutual-credit ledger in the pod schema (`services/cc-gateway`) exposing the B3 §9 gateway API; the Credit Commons node is the migration target. Inter-pod clearing disabled.
- ADR-24 Open records are stored in the pod schema in `org.bioregion.*` lexicon shape and served by `services/appview`; ATProto PDS/firehose is a follow-up. Records carry `bioregion` and `placeId`.
- ADR-25 Wallet is a browser PWA in `apps/web` (`/wallet`) using `@noble` keys in IndexedDB; Expo app and hardware keystore are follow-ups. The same `@passport/credential-core` is the engine for both.
- ADR-26 Single deployable: `apps/web` (Next.js 16 App Router) hosts all web apps and mounts all service handlers under `/api/<service>/…`; services remain separate packages so they can be split out.
- ADR-27 Pod signing keys are encrypted at rest with `POD_KEY_ENCRYPTION_KEY` (AES-256-GCM) in `platform.pod_keys`; KMS is a follow-up.
- ADR-28 POS adapters are interface-only stubs (`services/pos-adapter`) with a manual-tender adapter; Square OAuth is a follow-up.

### 4.5 Service handler shape
```ts
export interface PodContext { slug: string; podDid: string; db: Db /* already scoped by withPod */; manifest: BioregionManifest; policy: TrustPolicy; now: () => Date; platformDomain: string }
export interface Route { method: 'GET'|'POST'|'PUT'|'DELETE'; path: string /* e.g. '/membership/apply' with ':id' params */; auth?: 'none'|'member'|'authority:<scope>'|'steward'|'operator'; handler: (ctx: PodContext, req: { params: Record<string,string>; query: Record<string,string>; body: any; session?: SessionClaims }) => Promise<{ status?: number; body: any }> }

```
`apps/web` provides `mountService(routes, basePath)` that resolves tenant, opens `withPod`, loads manifest/policy from `platform.pods`, checks `auth` against the session cookie (`passport_session`, verified with `readSession`), and dispatches.

Auth for members: `POST /api/vta/session` with a VP (challenge from `GET /api/vta/challenge`) → `verifyDTG` → session cookie. Operator/steward auth: `authority:pep:review` / `authority:registry:propose` VACs presented the same way; a break-glass `OPERATOR_TOKEN` env for the first pod operator.
